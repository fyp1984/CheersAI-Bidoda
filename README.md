# 投标智囊团

**面向企业与个人自用的智能投标平台。** 把「招标文件解析 → 目录编排 → 全局事实设定 → 正文生成 → 导出 Word → 查重 / 废标项 / 暗标合规检查」这条投标准备主线，收进一台电脑上的本地桌面工作区，按一套固定流程把标书从零做到可复核的初稿。

| 项 | 值 |
|---|---|
| 产品名称 | 投标智囊团（工程代号 `bidoda`，用于仓库 / 可执行体 / 内部标识） |
| 品牌 | CheersAI（出品方与技术支持） |
| 仓库 | `CheersAI-Bidoda` |
| 上游 | 开源项目 [OpenBidKit / 易标投标工具箱](https://github.com/FB208/OpenBidKit_Yibiao)（AGPL-3.0-only） |
| 文档基线 | `02-需求分析/bidoda-产品PRD-V3.1-2026-11-12.md`、`03-架构与设计/bidoda-技术方案-V5.1-2026-11-12.md` |

## 一、产品定位

| 项 | 结论 |
|---|---|
| 服务对象 | 企业与个人的**自用**投标准备，面向内部参与投标准备的人员 |
| 核心场景 | 拿到招标文件后，完成解析、目录、事实设定、正文生成与导出，并做查重、废标项与暗标检查 |
| 部署形态 | macOS / Windows 本地桌面工作区，配置、缓存与生成结果全部留在本机 |
| 使用边界 | 同一法律主体内部、单机使用；**不对外销售、不对外分发、不向公众提供网络服务** |

一句话：把一套已经跑通的标书生产能力，装进投标人自己的电脑里，不依赖外部服务、不上传标底资料。

---

## 二、核心能力（六步主流程）

**选标书 → 生成设置 → 招标文件解析 → 目录 → 全局事实设定 → 生成正文导出 Word。** 六步固定流程，正文任务启动后生成设置自动锁定，避免中途改配置导致前后文口径不一致。

| 类别 | 能力 |
|---|---|
| 需求解析 | 18 个预设解析项，覆盖项目信息、评分要求、无效标与废标项等 |
| 事实与知识 | 文档知识库（上传 → 解析 → 全库检索 → 生成时勾选）、资信库（含 `valid_from` / `valid_to` 有效期）、全局事实设定 |
| 质量检查 | 标书查重、废标项检查、暗标合规检查（C# 确定性规则，含隐私 / 字体 / 页面 / 表格 / 一致性等类别） |
| 扩展场景 | 多标段 / 多阶段、商务标、可研报告、AI 生图、模板样式、图文混排、字数控制、插件系统、断点续跑 |
| 模型接入 | OpenAI-like API、ollama、LM Studio 等本地模型，由用户自行配置 |
| 产物 | Word 正文导出；每步产物落盘在本机，可追溯、可回退 |

## 三、产品边界（先说清楚不做什么）

- **不承诺中标**，不输出任何形态的中标率、胜率或概率数字，不对招标结果作预测或保证。
- 生成质量由上游版本决定：上游的「怎么写」含允许模型为缺失信息补写具体内容的档位，**生成结果一律视为初稿**，须人工核对数字、编号、名称、资质与业绩，不得直接递交。
- 在线服务（标讯、精选资源、官方账号、插件市场、模型信息、许可证与统计）依赖外部网络，离线环境下这些入口可能不可用；本地工作区与生成主流程不因此失效。
- 应用内自动更新**已禁用**：其 `publish` 指向上游官方 Release，一旦触发会把应用换回官方版本并覆盖品牌层。升级改走外层的受控重放（见第七节）。

## 四、工程架构：三层

产品不在上游进程内扩展，也不 fork 上游仓库。上游是只读黑盒，全部改动集中在品牌层，运行与验收由外层闸门把关。

| 层 | 内容 | 约束 |
|---|---|---|
| **L0 上游黑盒（只读）** | 上游官方 Release 原样落盘 | 不 fork、不 diff、不改任何业务逻辑文件；AGPL-3.0-only |
| **L1 品牌换皮层** | `brand/brand.json`（唯一事实源）、`apply.mjs`（重放）、`make-icons.sh`（图标）、`deploy/`（容器 / Windows 路径） | 只替换**中文品牌字样 / 应用名 / 图标**；ASCII 技术标识符一律不动 |
| **L2 运行与验收层** | `dist/bidoda.app`、`verify.mjs`（产物内部断言）、`REBRAND-REPORT.json`、版本闸门 | 验收全绿才切换版本指针；失败保留上一版回滚 |

数据流：**上游产物 → 换皮重放 → 产物验收 → 本地运行**；上游每发一版，都从第一步重跑一遍完整链路。

**「不改上游代码」的准确含义**：不是「一个文件都不碰」，而是改动**集中、隔离、可重放，且不与上游版本产生需要人工合并的冲突**。官方产物的品牌资源必然要被替换，只要这些替换由一份清单加一个脚本一次生成，上游源码树始终干净，升级时没有 diff 要合并。关键判据是：**品牌字样是中文（`易标`），内部标识符是 ASCII（`window.yibiao`）**——只替换中文品牌字样，天然避开技术标识符。

## 五、仓库结构

| 路径 | 内容 |
|---|---|
| `brand/brand.json` | 品牌替换的唯一事实源：替换项、保护串、白名单、版本锁、域同步策略 |
| `brand/apply.mjs` | 重放脚本：解压官方包 → 复制为 `bidoda.app` → 换皮 → ad-hoc 重签名 → 生成报告；支持 `--dry-run` / `--level 1` / `--freeze-baseline` / `--selftest` |
| `brand/verify.mjs` | 验收脚本：断言落到产物**内部实际内容**（逐文件 sha256、中文品牌字样已清除、ASCII 标识符仍存在、图标哈希一致、版本自报一致、域同步闸门） |
| `brand/make-icons.sh` | 由 CheersAI 源图生成 `.icns` / `.ico` / 各尺寸 PNG，**保持上游原文件名**以免图标引用断链 |
| `brand/assets/` | CheersAI Logo 源图与生成后的全套图标 |
| `brand/ACKNOWLEDGEMENTS.md` | AGPL-3.0 归属与许可声明，随产物一并保留 |
| `brand/README.md` | 本地运行、升级、合规与排障操作手册 |
| `deploy/mac-rename-brand.py` | macOS 侧改名：主可执行体与四个 Helper 包整体换牌，与 `CFBundleExecutable` 保持一致 |
| `deploy/orbstack/` | 容器化联调：Ubuntu + Xvfb + noVNC，浏览器访问完整 GUI，用于在容器内跑通全流程 |
| `deploy/windows/` | Windows 安装包构建与联调指引（与 macOS 同源技术方案） |

`releases/`（上游官方安装包）、`vendor/`（上游只读基线）、`work/`（中间产物）、`dist/`（换皮产物）为本地工作目录，不入库。

## 六、快速开始（macOS）

```bash
# 0) 取上游官方产物（本机浏览器下载）放入 releases/
#    GitHub: https://github.com/FB208/OpenBidKit_Yibiao/releases
#    文件示例: Yibiao-2.31.7-mac-arm64.zip

# 1) 生成图标（需先放品牌源图）
cp <cheersai-logo.png> brand/assets/cheersai-logo.png
bash brand/make-icons.sh

# 2) 装一次 asar 工具（Level 2 文本替换需要）
npm install --no-save @electron/asar

# 3) 替换规则自证：必须全绿
node brand/apply.mjs --selftest

# 4) 先看变更清单，不落产物
node brand/apply.mjs --zip releases/Yibiao-2.31.7-mac-arm64.zip --dry-run

# 5) 确认无误后正式重放
node brand/apply.mjs --zip releases/Yibiao-2.31.7-mac-arm64.zip

# 6) 验收：失败返回非 0
node brand/verify.mjs

# 7) 启动
open dist/bidoda.app
```

只想最快看到界面：加 `--level 1`，只换应用显示名、图标与 `Info.plist`，跳过 asar，也不需要 `@electron/asar`。首次启动若被 macOS 拦截，用「访达 → 右键 → 打开」放行一次。

容器内联调（不依赖本机 macOS 打包）见 `deploy/orbstack/`：容器启动后浏览器访问 `http://localhost:6080/` 即可操作完整 GUI。

## 七、上游升级：受控重放，而不是跟随自动更新

上游迭代频繁，数据库结构持续演进，所以「丝滑升级」不是跟着自动更新，而是把升级变成一次**可重复的重放 + 闸门**：

1. 下载新版官方产物放入 `releases/`；**不在应用内点检查更新**。
2. 同一份官方原版首次建立基线：`node brand/apply.mjs --freeze-baseline --zip <官方原版 zip>`，逐文件 sha256 写入 `vendor/baselines/<版本>/`。
3. `--dry-run` 预览变更集；变更集异常扩大即说明上游结构变了，须复核 `brand.json`。
4. 正式重放 → `node brand/verify.mjs` 全绿才切换版本指针。
5. 失败则保留上一版产物（`bidoda.app.prev-<时间戳>` 移动保留、不删除）回滚，新版列入待适配。
6. 每次重放生成《换皮报告》，记录上游版本号、逐文件哈希、变更集与警告。

### 单一真相源与防杂交（最高优先级）

本产品永远是「某一确切上游版本 + 品牌换皮」的**原子镜像**，不存在半同步、半旧版、部分打补丁的杂交态：

- **单一真相源**：版本锁死在 `brand.json` 的 `versionLock.pinnedVersion`；运行实例通过 `Contents/Resources/BIDODA-PIN.json` 自报它对应哪个上游版本。
- **零补丁**：任何业务修正只能源于「重放换皮到新版上游」，绝不在 `vendor/` 原版或 `dist/` 产物里手改逻辑。
- **二进制决策**：上游发新版后只有「全量采纳」或「整体阻断」两条路，禁止部分采纳与新旧混装。
- **防杂交技术闸门**：`verify.mjs` 将当前产物与官方原版基线逐文件比对，任何落在换皮白名单之外的差异一律判为漂移并阻断。
- **域同步闸门**：上游新增「议标 / 竞争性谈判 / 单一来源采购 / 询价」等采购方式类域元素时，未在 `brand.json` 的 `domainSyncPolicy.reviewedAndAdopted` 登记并经合规复核，升级**默认阻断**，绝不静默放行。

## 八、验收标准

验收断言一律落到产物**内部实际内容**，不以「文件存在」或「命令返回 0」代替：

| 断言 | 证明什么 |
|---|---|
| asar 内逐文件 sha256 与重放报告一致 | 非白名单文件字节未变 |
| 变更集 ⊆ 白名单 | 没有意外改动 |
| 不含中文品牌字样、页面 `<title>` 正确 | 品牌替换真的生效 |
| `window.yibiao`、`yibiao-asset`、`yibiao-client` 仍存在 | 技术标识符没被误改 |
| `CFBundleName` / `CFBundleDisplayName` 正确，`CFBundleIdentifier` 未变 | 应用标识正确且既有配置不丢 |
| 图标内容哈希与 CheersAI 源图一致 | Logo 生效 |
| `codesign --verify --deep --strict` 通过 | macOS 可启动 |
| 归属声明 / LICENSE / NOTICE 存在 | 归属完整 |

替换规则自身须先通过正例与反例自证（`node brand/apply.mjs --selftest`）：**校验脚本没被已知正例与反例自证过，等于没有校验。**

## 十、已知风险与使用纪律

| 风险 | 处置 |
|---|---|
| 生成内容含模型补写的缺失信息 | 全量人工复核；缺口留空并入待补清单，不虚构资质、业绩、证书与财务数据 |
| 上游结构调整导致品牌层失效 | 升级前 `--dry-run` + 验收闸门，失败不切版本 |
| 上游在线服务不可用 | 本地主流程不依赖；在线功能降级，不影响生成与导出 |
| 许可证边界被突破 | 单人单机、同一法律主体内部；形态变化前重新评估 |
| 改动 `.app` 后未签名 | 脚本内置 ad-hoc 重签名；漏签会导致 macOS 拒绝启动 |
| `CFBundleIdentifier` 被误改 | 保持原值不变，否则会切换 Electron `userData` 目录，既有配置看似「丢失」 |
